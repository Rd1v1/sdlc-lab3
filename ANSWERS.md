# LAB 3 — ответы для защиты

## 1. Что такое хэш?

Хэш — результат вычисления хэш-функции от входных данных. Один и тот же алгоритм с одинаковыми входными данными и параметрами даёт одинаковый результат. MD5 выдаёт 128 бит, SHA-1 — 160 бит. Для парольных алгоритмов bcrypt и Argon2id строка хранения содержит также параметры вычисления и соль.

## 2. Почему нельзя просто расшифровать хэш?

Хэширование не использует ключ для обратного преобразования. Разные входные строки могут иметь одинаковый хэш, поэтому однозначного обратного преобразования нет. Программа ищет подходящий кандидат и проверяет совпадение; математически это не гарантирует восстановление именно исходной строки.

## 3. Как работает полный перебор?

Программа последовательно получает кандидаты пароля, вычисляет для каждого нужный хэш и проверяет совпадение с целевым. Поиск заканчивается при совпадении, исчерпании заданного набора или остановке пользователем.

## 4. Как генерируются кандидаты?

В [candidates.py](lab3/src/candidates.py) функция `iter_candidates` проходит длины от `min_length` до `max_length`. Для каждой длины `itertools.product` создаёт все комбинации символов алфавита с повторениями. Например, для `ab` и длин 1–2 порядок такой: `a`, `b`, `aa`, `ab`, `ba`, `bb`. Генератор выдаёт кандидаты по одному, не сохраняя весь набор в памяти.

## 5. Как вычисляется хэш кандидата?

На CPU MD5 и SHA-1 вычисляются через `hashlib`, bcrypt проверяется через `bcrypt.checkpw`, Argon2id — через `PasswordHasher.verify`. Сгенерированные строки передаются в UTF-8, строки словаря — в исходных байтах. На GPU [gpu.py](lab3/src/gpu.py) передаёт пакеты кандидатов OpenCL-ядрам. Программа не запускает hashcat для выполнения своего поиска.

## 6. Как сравнивается результат?

Для MD5 и SHA-1 на CPU сравниваются шестнадцатеричные строки. Библиотеки bcrypt и Argon2id проверяют кандидат с солью и параметрами из целевого хэша. На GPU вычисленный результат сравнивается с байтами целевого хэша. Пароль появляется в поле `found_password` только после подтверждённого совпадения.

## 7. Как устроено параллельное выполнение?

На CPU `--workers 1` выполняет последовательный цикл, а большее число воркеров включает `ThreadPoolExecutor`. Потоки получают кандидаты из общего генератора. На GPU `--workers N` задаёт число кандидатов в пакете. Для интерактивной таблицы поиск выполняется в отдельном служебном потоке, чтобы интерфейс оставался отзывчивым; это не дополнительный воркер перебора.

## 8. От чего зависит размер пространства перебора?

От числа символов алфавита `A` и выбранных длин. Для одной длины `L` число вариантов равно `N = A^L`. Для диапазона длин: `N = A^min_length + … + A^max_length`. Например, `abc` при длине 3 даёт `3^3 = 27` вариантов, а `ab` при длинах 1–3 даёт `2 + 4 + 8 = 14` вариантов.

## 9. Почему увеличение длины резко усложняет подбор?

Каждый дополнительный символ увеличивает число вариантов в `A` раз. Для десяти цифр длина 3 даёт 1000 вариантов, длина 4 — 10 000. При постоянной суммарной скорости `R` проверок в секунду полный перебор займёт приблизительно `N / R` секунд, без учёта подготовки. При остановке после находки время зависит также от позиции пароля в порядке перебора.

## 10. Как измеряется время и скорость?

В функциях поиска используется `time.perf_counter()`. Поле `elapsed_seconds` содержит время работы поиска; `candidates_checked` — число завершённых проверок. В CLI скорость оценивается как число проверок, делённое на прошедшее время. `gpu_kernel_seconds` отдельно учитывает время выполнения OpenCL-ядер по событиям GPU.

В сравнительной таблице README измерено **полное время отдельного процесса**, включая запуск Python или hashcat и подготовку GPU. Это другая величина, чем время только GPU-ядер или пиковая скорость хэширования.

## 11. Какие результаты получены и как их понимать?

В [README](README.md#сравнение-с-hashcat) приведены два режима для всех 16 хэшей задания: четыре алгоритма и четыре уровня пароля. Для каждой пары инструмента и хэша выполнен один запуск с внешним лимитом 15 секунд; всего 64 запуска. Общие столбцы содержат сумму времени четырёх отдельных процессов и число найденных паролей из четырёх. В столбцах алгоритмов записаны пары «Моё приложение / hashcat»: SHA-1 и MD5 — в секундах, bcrypt и Argon2id — в часах.

Знак ✓ означает подтверждённую находку, «И» — исчерпание набора без совпадения, «Л» — отсутствие найденного пароля за 15 секунд. Число с «Л» — нижняя граница времени поиска, а не время подбора. Без словаря перебираются 1 100 000 вариантов алфавита `123456aple` длиной 5–6. Со словарём передаётся полный RockYou, но после находки поиск прекращается.

Уровни easy–very_hard взяты из задания. Они не меняют cost bcrypt или параметры Argon2id: эти параметры одинаковы внутри каждого алгоритма. По одиночным коротким запускам с подготовкой GPU нельзя судить о пиковой скорости. Условия и исходные измерения находятся в [REPORT.md](REPORT.md) и каталоге `reports/`.

## 12. Чем отличаются исследуемые алгоритмы?

| Алгоритм | Особенность, существенная для перебора |
| --- | --- |
| MD5 | Быстрая хэш-функция с результатом 128 бит; в приложении проверяется без соли |
| SHA-1 | Быстрая хэш-функция с результатом 160 бит; в приложении проверяется без соли |
| bcrypt | Парольный алгоритм с солью и настраиваемым параметром сложности `cost` |
| Argon2id | Парольный алгоритм с солью, настраиваемыми затратами памяти, проходами и параллелизмом |

Быстрое вычисление удобно для проверки целостности, но позволяет быстрее проверять догадки о пароле. Увеличение длины хэша само по себе не определяет стоимость подбора пароля.

## 13. Что такое соль?

Соль — дополнительное значение, участвующее в хэшировании пароля. Разные соли дают разные результаты для одного пароля и мешают использовать одну готовую таблицу хэшей для множества записей. Соль хранится вместе с хэшем и не является секретом. При проверке нужно использовать соль целевого хэша. Для реального хранения паролей каждой записи нужна случайная соль; фиксированная соль в контрольных примерах служит воспроизводимости эксперимента.

## 14. Что означает параметр сложности bcrypt?

`cost` задаёт объём внутренней вычислительной работы. В записи `$2a$10$...` значение сложности равно `10`. Работа основной части bcrypt растёт примерно как `2^cost`: увеличение `cost` на единицу примерно удваивает её. `cost` не задаёт длину пароля и число кандидатов.

## 15. Что означают параметры Argon2id?

В строке `$argon2id$v=19$m=65536,t=3,p=2$...` значение `v` обозначает версию, `m` — объём памяти в КиБ, `t` — число проходов, `p` — число линий параллельной обработки внутри одного вычисления. Здесь `m=65536` соответствует 64 МиБ. `p` не равно числу воркеров приложения. Пакет из нескольких Argon2id-кандидатов требует памяти для каждого кандидата.

## 16. Приложение принимает только хэши из задания?

Приложение принимает собственные значения MD5, SHA-1, bcrypt и Argon2id в поддерживаемом формате и диапазоне параметров. `HashTarget.parse` в [hashes.py](lab3/src/hashes.py) определяет алгоритм по длине шестнадцатеричной строки или префиксу. Файл `assignment-hashes.json` содержит тестовые данные и не ограничивает допустимые значения хэшей.

## 17. Можно ли определить длину пароля по хэшу?

По хэшам поддерживаемых алгоритмов длина исходного пароля не определяется. Например, MD5 всегда представлен 32 шестнадцатеричными символами независимо от длины пароля. Диапазон длин задаётся для поиска. Отсутствие совпадения означает, что подходящий пароль не найден в проверенном наборе.

## 18. Чем поиск по словарю отличается от полного перебора?

Полный перебор генерирует все комбинации выбранного алфавита и длин. Словарь задаёт готовую последовательность кандидатов. Режим `--wordlist` читает файл построчно в бинарном виде, удаляя только окончания строк. Приложение не загружает весь словарь в память и не подсчитывает все строки перед началом поиска. Параметры алфавита и длин в словарном режиме не фильтруют кандидаты.

## 19. Чем поток отличается от процесса?

Процесс имеет собственное виртуальное адресное пространство. Потоки одного процесса используют общую память, но у каждого есть свой стек и контекст выполнения. Общая память упрощает обмен данными между потоками и требует синхронизации. В приложении CPU-воркеры являются потоками; отдельные процессы для перебора не создаются.

## 20. Что означает 32 GPU-воркера?

Это до 32 кандидатов в одном пакете GPU. Число не обозначает количество видеокарт, ядер GPU или потоков операционной системы. OpenCL организует вычислительные потоки согласно ядру алгоритма. Если осталось меньше 32 кандидатов, последний пакет будет короче. Приложение выбирает первую доступную GPU; при её отсутствии сообщает об ошибке.

## 21. Почему больше воркеров не всегда означает быстрее?

Создание и переключение потоков, блокировки и обмен данными требуют времени. На GPU есть затраты на подготовку и передачу пакетов. Argon2id дополнительно ограничивает доступная память. Для короткой задачи эти расходы могут перекрыть выигрыш от параллельного выполнения, поэтому оптимальное число воркеров определяется замерами.

## 22. Как влияет GIL?

В обычной сборке CPython с GIL несколько потоков не исполняют Python-байткод одновременно. Поэтому потоки не гарантируют ускорения вычислительного Python-кода. Нативные библиотеки могут выполнять часть работы с освобождением GIL, а OpenCL-ядра работают на GPU. Результат нужно оценивать для конкретного алгоритма и режима.

## 23. Как предотвращаются пропуски кандидатов и гонки?

В [cpu.py](lab3/src/cpu.py) получение следующего кандидата и изменение общего состояния защищены `threading.Lock`. Генератор выдаёт каждый элемент одному воркеру, а вычисление хэша происходит вне блокировки. Для интерфейса создаются снимки состояния в виде кортежей. Одинаковые строки, повторяющиеся в словаре, остаются отдельными кандидатами и могут проверяться несколько раз.

## 24. Как останавливается поиск?

При совпадении CPU-воркер устанавливает `threading.Event`, остальные завершаются при следующей проверке события. Уже начатые проверки могут успеть завершиться и учитываются в счётчиках. На GPU поиск прекращается после обработки текущего пакета. Ctrl+C передаёт запрос отмены; программа завершает поиск, освобождает ресурсы и возвращает код `130`. GPU-ядро не прерывается принудительно посередине вычисления.

## 25. Что показывает таблица воркеров?

Для каждого воркера показаны номер, состояние, число завершённых проверок, текущий наблюдаемый кандидат и подтверждённый найденный пароль. Кандидат может не совпадать с целевым паролем. Поле результата заполняется только при состоянии `found`. Интерфейс обновляет снимки примерно раз в 0.1 секунды, поэтому не показывает отдельно каждую быструю проверку.

## 26. Как таблица работает при большом числе воркеров?

В [terminal.py](lab3/src/terminal.py) используется прокручиваемый `TextArea` библиотеки `prompt_toolkit`. Размер окна определяет видимую область; все строки сохраняются в таблице. Стрелки и PgUp/PgDn позволяют прокручивать данные, Ctrl+Home/End — переходить к началу и концу. При изменении кандидатов сохраняется выбранная строка. JSON выводится в stdout, прогресс — в stderr. При перенаправлении прогресса итоговая таблица печатается один раз.

## 28. Какие ограничения есть у приложения?

Без словаря: длины 1–8, алфавит до 128 уникальных символов, до 2 млн кандидатов. Файл словаря — до 256 МиБ. Для bcrypt поддерживается `cost` 4–12, для Argon2id — версия 19, память до 256 МиБ, 1–10 проходов и 1–8 линий параллелизма. На GPU Argon2id поддерживает результат длиной 32 байта; допустимый размер пакета дополнительно ограничивается памятью GPU.

Кандидаты GPU длиннее 256 байт и кандидаты bcrypt длиннее 72 байт пропускаются. Установленные приложением верхние пределы объёма работы не являются требованиями задания и не означают некорректность хэша за их пределами.

## 29. Что проверяют тесты?

Проверяются четыре алгоритма, заданные и самостоятельно созданные хэши, порядок кандидатов, найденный пароль и исчерпание набора. Отдельно проверяются потоки, счётчики, словарь, ошибки, отмена и результаты каждого воркера. Тесты GPU выполняют реальные вычисления OpenCL. Тесты терминала проверяют прокрутку, обновления и изменение окна для числа строк вплоть до 4096.

## 30. Как кратко показать работу на защите?

Из корня подготовленного проекта выполнить:

```powershell
.venv/Scripts/python.exe main.py 9df62e693988eb4e1e1444ece0578579 --alphabet abc --min-length 3 --max-length 3 --workers 2
.venv/Scripts/python.exe main.py 9df62e693988eb4e1e1444ece0578579 --alphabet abc --min-length 3 --max-length 3 --gpu --workers 32
.venv/Scripts/python.exe main.py 9df62e693988eb4e1e1444ece0578579 --alphabet ab --min-length 3 --max-length 3 --no-progress
.venv/Scripts/python.exe main.py invalid --no-progress
```

Первые две команды находят `ccc` и возвращают код `0`. Третья исчерпывает восемь вариантов, не находит пароль и возвращает `1`. Четвёртая сообщает об ошибке формата хэша и возвращает `2`. Затем показать генератор, проверку хэша, распределение работы и сравнительную таблицу README. Hashcat запускается отдельно командами из отчёта.
